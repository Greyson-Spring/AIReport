# 排障思路与方法（前端问题排查实战记录）

> 这份文档教你**怎么面对代码问题**。不是背答案，而是学会"从哪里下手、怎么一步步定位、怎么修复"。
> 以我们刚修的 3 个前端问题为例，还原完整思考过程。

---

## 一、面对问题，先走这 6 步（通用框架）

遇到 bug，别急着改，按顺序来：

```
第1步 复现 + 说清楚
      "什么时候发生？期望什么？实际什么？"
      （比如：点击文件夹 → 行高变了，期望不变）
      ↓
第2步 找代码入口
      这个功能在哪个文件？哪个组件？
      （搜索关键词 / 从点击事件的函数反查）
      ↓
第3步 读数据流
      数据从哪来？点击触发了什么？模板怎么渲染？
      （前端 = 模板(template) + 逻辑(script) + 样式(style)）
      ↓
第4步 缩小范围
      是"之前好的，最近改坏了"（回归）？还是本来就这样？
      最近改了什么？先怀疑最近的改动。
      ↓
第5步 提出假设 → 验证
      猜一个原因 → 读代码验证 / 加 console.log 验证
      ↓
第6步 最小改动修复 + 回归测试
      只改必要的地方，改完确认没影响其他功能
```

**核心心法：先找到"问题在哪"，再想"怎么改"。** 90% 的时间花在定位，改代码只占 10%。

## 二、实战记录 1：文件夹行高变化

### 现象
点击自定义文件夹那行，行高/文字位置会变；未分类的公众号行不会变。

### 定位过程（第2、3步）
```
① 打开文件 web_ui/src/views/article/ArticleListDesktop.vue
② 搜"文件夹"相关 → 找到模板里 .folder-item 那一行（约96行）
③ 读这一行发现：选中时(active) 会多渲染一个"删除按钮"
   <a-button v-if="activeItem是文件夹 && 选中">
     <icon-delete />
   </a-button>
④ 关键理解：这个按钮是"条件渲染"(v-if)
   → 没选中时不渲染(不占空间)
   → 选中时渲染(占用空间)
   → 布局就变了！
```

**假设**：按钮的加入改变了 flex 布局，撑高了行。

### 第一次修复（不彻底）
```
用固定宽度的 <span> 包住按钮，预留 24px 空间
→ 理论上按钮出现不影响布局
→ 但按钮实际渲染尺寸 > 24px，还是溢出，问题没根治
```

### 第二次修复（根治）
```
关键点：要让按钮"始终存在，只是不可见时看不见"
改用 CSS 的 visibility（可见性），不是 v-if（渲染与否）：
  visibility: hidden  → 占空间但看不见
  visibility: visible → 占空间且看得见
→ 按钮始终占着同样的空间 → 布局永远不变 → 行高稳定 ✅
```

**学到的点**：
- `v-if`（渲不渲染）会改变布局；`visibility`（看不看得见）不影响布局。
- 想让"出现一个元素但不改变布局"，用 `visibility` 或绝对定位，别用 `v-if`。

## 三、实战记录 2：文件夹加载慢（2-3秒）

### 现象
点击"芯片"文件夹（44个公众号），右侧文章要等 2-3 秒。

### 定位过程（第2、3步）
```
① 搜"文件夹点击" → 找到 handleLeftItemClick
② 里面发现：点击文件夹调用 fetchArticlesByFolder(folder)
③ 读这个函数（约954行）：
   const mpIds = folder.feeds.map(f => f.id)
   const promises = mpIds.map(mpId => getArticles({pageSize: 100, mp_id: mpId}))
   const results = await Promise.all(promises)  // 44次请求同时发!
   ...把所有文章合并、排序...
```

**发现问题根源**：
```
44个号 × 每号请求1次 = 44次HTTP请求
44次 × 每号返回100篇 = 最多4400篇文章在前端合并排序
→ 又慢又卡
```

### 修复
```
把 pageSize 从 100 降到 20
→ 44×20 = 880篇，合并排序轻多了
→ 明显变快
```

### 根治方向（还没做）
```
更好的方案：改后端，支持"一次查多个 mp_id"
  后端加一个接口: WHERE mp_id IN (…)
  → 44次请求变成1次 → 会快非常多
```

**学到的点**：
- 慢 = 找"循环/并发"+"数据量"。"44次请求 + 每号100篇"就是罪魁祸首。
- 前端优化思路：减请求数（合并）、减数据量（降pageSize）。
- 从"事件入口"反查函数，顺着数据流找到慢的地方。

## 四、实战记录 3：改水印文字

### 现象
页面有个很浅的水印 "Power By Rachel Design@10.188.26.61"。

### 定位过程
```
① 搜索源码 web_ui/src 里的 "rachel" → 找到了几个(但都不是水印)
② 搜索 "design@"/"power" → 源码里没直接找到
③ 换思路：搜构建产物(static/assets/*.js)
   用 python 读 JS 文件，搜 "design" 上下文
   结果发现: computed(() => `Power By Rachel Design@${window.location.hostname}`)
④ 反查源码 → 在 BasicLayout.vue 第21-24行
```

**关键技巧**：**运行时显示的字符串，可能由代码拼接生成**（这里就是 `模板字符串` + 变量拼出来的）。源码里搜不到完整句子时，搜"组成部分"（design / hostname / 变量名），或在构建产物里搜。

### 修复
```
把默认字符串 'Power By Rachel Design' 改成 'Power By Armchina'
（还发现可以用环境变量 VITE_APP_COPYRIGHT 覆盖）
```

**学到的点**：
- 动态生成的文字（带变量/IP）在源码里是拼出来的，搜"关键词片段"。
- 用 python/grep 读构建产物，能帮你从"运行时现象"反查"源码位置"。

## 五、可复用的定位工具清单

| 场景 | 用什么命令/方法 |
|---|---|
| 找某个文字在哪个文件 | `grep -rn "关键词" web_ui/src --include="*.vue"` |
| 找点击事件触发什么 | 模板里 `@click="函数名"` → 在 script 里搜 `const 函数名` |
| 找样式问题 | 模板里的 class → 搜 `.class名` 的 CSS |
| 找构建产物里的字符串 | `python` 读 `static/assets/*.js`，用 `re` 搜上下文 |
| 确认我的假设 | 在代码里加 `console.log(...)`，打开浏览器 F12 看输出 |
| 看是"最近改坏"还是"一直这样" | `git log` / `git diff` 看最近改动 |

## 六、给新手的练习方法（怎么培养手感）

1. **先读懂，再动手**：改之前先把这个函数的输入、输出、做了什么讲出来。
2. **用 console.log 当"探针"**：不确定时打一行日志，看实际值，验证假设。
3. **小步走**：一次只改一处，改完就测，别攒一堆一起改。
4. **学会读报错**：报错信息里有文件路径和行号，那就是定位线索。
5. **从"入口"开始**：用户点了什么 → 找到那个按钮 → 顺着函数往下追。
6. **区分"现象"和"原因"**：现象（卡、变高、错字）只是表面，原因在数据流和逻辑里。

---

## 七、这套方法的适用范围

这套"定位 → 假设 → 验证 → 最小修复"的方法，**前后端通用**：
- 前端：模板+逻辑+样式
- 后端：路由 → 函数 → 数据库查询
- 核心都是：**顺着数据流走，找到问题的源头，而不是在表面打补丁**
