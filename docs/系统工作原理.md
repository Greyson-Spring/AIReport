# WeRSS 系统工作原理完全指南（小白版）

> 用最通俗的方式讲清楚：你的网站是怎么工作的、公众号文章是怎么被抓进来的、为什么需要一个 Edge 浏览器、数据是怎么从微信读书跑到你屏幕上的。

---

## 一、一句话总结

你的系统 = **一个网站**（给你看文章）+ **一个采集器**（去抓文章）+ **一个"签名装置"**（让你能抓到微信读书的文章）。

这三样配合起来，就能定时自动把公众号文章抓进来，在网页上展示。

## 三、看文章的流程（前端 ←→ 后端 ←→ 数据库）

这是你每天打开网站做的事，**和采集无关**：

```
① 你打开 localhost:8001，登录
② 前端页面加载 → 向后端发请求: GET /api/v1/wx/articles
③ 后端收到请求 → 到数据库查"有哪些文章"
④ 数据库返回文章数据
⑤ 后端把数据转成 JSON 返回给前端
⑥ 前端把文章渲染成列表，显示在网页上
```

**关键点：** 这一步只是"读取"，数据库里已经有文章了。文章是**采集器**事先放进去的。

---

## 四、文章是怎么来的？（采集流程）

文章不是凭空出现的，是**采集器定时去抓**的。完整路径：

```
① 定时任务到点（比如每天9点）→ 触发后端
② 后端启动"采集器"(weread_mp模式) → 对每个公众号发起采集
③ 采集器需要向微信读书要文章列表 → 但微信读书有"反爬墙"
④ 采集器把请求交给【宿主机代理】
⑤ 代理命令【Edge浏览器】在"阅读器页"里发请求
⑥ Edge浏览器(已登录微信读书)发出请求 → 微信读书返回文章列表 ✅
⑦ 代理把文章数据传回采集器
⑧ 采集器把文章存进数据库
⑨ 你打开网站 → 看到文章
```

## 五、最关键的疑问：为什么必须开一个 Edge + 阅读器页？

这是整个方案最绕、也最核心的地方。用大白话解释：

### 微信读书设了一道"墙"

微信读书的接口 `/web/mp/articles` 有一个**动态签名机制**（内部叫 x-wrpa-0）：
- 每次请求都要带一个**实时算出来的签名**
- 这个签名只有**浏览器里运行的 JS/WASM 代码**能算出来
- 而且必须是在"**阅读器页**"的上下文里算的

### 为什么 Python 直接请求不行？

```
Python 直接发请求 (requests.get)
  = 打了个电话说"给我文章"
  = 没有浏览器 → 算不出签名 → 微信读书回复 -2041（拒绝）❌
```

### 为什么 Edge + 阅读器页就行？

```
Edge 浏览器打开"阅读器页"
  = 浏览器真的把页面加载了，页面里的签名程序(WASM)运行起来了
  = 这时候在页面里发请求，浏览器自动算好签名
  = 微信读书一看"哦，是正常浏览器在正常页面里请求" → 放行 ✅
```

**打个比方：**
```
微信读书 = 一栋有门禁的大楼
Python 直接请求 = 打电话报门禁号 → 门卫要求刷脸 → 你没法刷 → 拒绝
Edge 开着阅读器页 = 一个真人站在摄像头前 → 刷脸通过 → 放行
宿主机代理 = 一个"办事员"，替你把请求递给那个真人
```

### 为什么要"你的"Edge？

- 需要**微信读书登录态**（Edge 里登录着微信读书，有你的 cookie）
- **真实浏览器**不容易被微信读书识别成自动化工具
- 所以必须借用你真实登录的 Edge

### 为什么"阅读器页"？

微信读书规定：请求必须在**阅读器页上下文**里发出才有效（它靠这个判断"是不是真人在正常使用"）。打开任意一个公众号的阅读器页就够了——**一个阅读器页可以查询所有公众号**。

## 六、宿主机代理是干嘛的？（翻译官）

```
容器(WeRSS)  ──POST http://host.docker.internal:9000/fetch──→ 宿主机代理
     "我要 MP_WXS_3089223813 这个号的文章"                    │
                                                             ▼
宿主机代理 ──CDP指令──→ Edge浏览器（在阅读器页执行fetch）
     "在页面里帮我发这个请求"                                   │
                                                             ▼
宿主机代理 ←──文章JSON─── Edge浏览器
     │
     ▼
容器(WeRSS) ←──文章JSON───  (采集器拿到数据，存进数据库)
```

**为什么要中间加个代理？** 因为 WeRSS 跑在 Docker 容器里，容器里没有你那个登录好的 Edge。代理就是**宿主机上的一个中转站**，让容器能指挥你的 Edge。

## 七、自动化是怎么实现的？（定时任务）

系统不靠你手动点"更新"，靠**定时任务**：

```
你配置的"消息任务"：
  - 抓哪些号：空 = 抓所有公众号
  - 什么时候抓：cron = "0 9,21 * * *" = 每天 9:00 和 21:00
        ↓ 到点自动触发
  - 后端启动采集器 → 对所有公众号逐个抓取 → 存数据库
```

**你添加新公众号也会自动纳入**：
```
你添加新号 → 下次定时任务(9点/21点)自动把它也抓了
```

## 八、添加新公众号的正确姿势

```
① 在微信读书里搜索并关注这个公众号（最关键！没关注就抓不到）
② 在网站里"添加公众号"
   → 添加时系统会立即抓一次 → 文章马上出现
   → 之后靠12小时定时任务持续更新
```

> 推荐顺序：**微信读书先关注 → 网站再添加**，这样添加后立刻就有文章。

## 十、常见疑问快答

**Q: 为什么不直接用公众号后台接口抓？（以前的方式）**
A: 腾讯 2026年7月底关闭了公众号后台的跨账号查询接口，那条路废了。微信读书是现在还通的路。

**Q: 为什么一定要开着 Edge？**
A: 微信读书的签名只能由真实浏览器算出来。关了 Edge，没人算签名，抓不了。

**Q: 微信读书里没关注的公众号能抓吗？**
A: 不能。微信读书只提供你已关注的号的文章。

**Q: 前端那个"微信读书管理页"是啥？**
A: 一个可选的网页界面，让你在网页上粘贴/管理微信读书的 Cookie 和 ticket。目前你的 Cookie 已经配在 `.env` 里了，这个页面是锦上添花，不配也能用。

**Q: 我电脑关机了，还能抓吗？**
A: 不能。采集依赖你电脑上的 Edge 和代理。要一直抓，电脑就得开着（或设开机自启）。
