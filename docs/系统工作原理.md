# WeRSS 系统工作原理完全指南（小白版）

> 用最通俗的方式讲清楚：werss网站是怎么工作的、公众号文章是怎么被抓进来的、为什么需要一个 Edge 浏览器、数据是怎么从微信读书跑到你屏幕上的。

---

## 一、一句话总结

你的系统 = **一个网站**（给你看文章）+ **一个采集器**（去抓文章）+ **一个"签名装置"**（让你能抓到微信读书的文章）。

这三样配合起来，就能定时自动把公众号文章抓进来，在网页上展示。

## 三、看文章的流程（前端 ←→ 后端 ←→ 数据库）

这是你每天打开网站做的事，**和采集无关**：

```
① 你打开 localhost:8001，登录
② 前端页面加载 → 向后端发请求: GET /api/v1/wx/articles
③ 后端收到请求 → 到数据库查"有哪些文章"
④ 数据库返回文章数据
⑤ 后端把数据转成 JSON 返回给前端
⑥ 前端把文章渲染成列表，显示在网页上
```

**关键点：** 这一步只是"读取"，数据库里已经有文章了。文章是**采集器**事先放进去的。

## 四、文章是怎么来的？（采集流程，逐步分解）

文章不是凭空出现的，是**采集器定时去抓**的。下面是**最具体**的流程，每一步对应什么代码/什么角色：

```
【触发】定时任务到点 或 你手动点"更新"
   ↓
【选号】读取 feed 表里的公众号 → 取出每个号的 mp_id（如 MP_WXS_3089223813）
   ↓ （weread_mp 采集器）
【要数据】采集器调用 _get_mp_articles_page(book_id=该号的mp_id)
   ↓ 采集器把 book_id 通过 HTTP 发给【宿主机代理】
【中转】宿主机代理(端口9000)收到请求
   ↓ 代理找到 Edge 里开着的"阅读器页"，通过 CDP 命令它执行一段JS
【执行】Edge 在阅读器页里运行: fetch('/web/mp/articles?bookId=MP_WXS_...')
   ↓ Edge 是真实浏览器 + 已登录微信读书 → 自动算好签名 → 微信读书返回文章JSON
【回传】代理把文章JSON传回容器的采集器
   ↓
【入库】采集器解析文章(标题/链接/时间) → 存进 articles 表
   ↓
【展示】你打开网站 → 前端从数据库读文章 → 显示出来
```

**一句话版：** 取 feed 表里每个号的 `mp_id` → 让 Edge 的阅读器页帮我们去微信读书要文章 → 拿到存进数据库 → 网页显示。**你的理解是对的！**

### 三个角色的比喻（对应代码）

| 角色 | 是谁 | 比喻 | 对应文件 |
|---|---|---|---|
| 采集器 | 容器里的后端 | 想拿文章的"采购员" | `core/wx/model/weread_mp.py` |
| 宿主机代理 | 你电脑上跑的小程序 | 采购员和真人的"传话员" | `tools/host_weread_agent.py` |
| 签名装置 | 你登录微信读书的 Edge | 能刷脸的"真人" | 就是你开的那个 Edge |

### `start_weread_host.bat` 是啥？

它就是"一键启动"按钮，双击后帮你把两个东西跑起来：
```
① 启动 Edge（带调试口9222，打开微信读书阅读器页）
② 启动宿主机代理（端口9000）
```
启动后它们常驻后台，采集器随时能调用。**相当于给"传话员"和"真人"上班打卡。**

## 五、最关键的疑问：为什么必须开一个 Edge + 阅读器页？

> **先澄清一个容易混淆的点**：用的是你电脑上登录微信读书的 **Edge**，不是 Docker 容器里那个 chromium。
> - **Edge**（你电脑上的真实浏览器）= 正在用，是"签名装置"
> - **Chromium**（容器里装的）= 我第一次尝试的"无头自动化浏览器"，被微信读书识别出是自动化而拒绝(-2041)，**没用上**
> 简单说：微信读书只信"真人浏览器"，不信"机器人浏览器"。

这是整个方案最绕、也最核心的地方。用大白话解释：

### 微信读书设了一道"墙"

微信读书的接口 `/web/mp/articles` 有一个**动态签名机制**（内部叫 x-wrpa-0）：
- 每次请求都要带一个**实时算出来的签名**
- 这个签名只有**浏览器里运行的 JS/WASM 代码**能算出来
- 而且必须是在"**阅读器页**"的上下文里算的

### 为什么 Python 直接请求不行？

```
Python 直接发请求 (requests.get)
  = 打了个电话说"给我文章"
  = 没有浏览器 → 算不出签名 → 微信读书回复 -2041（拒绝）❌
```

### 为什么 Edge + 阅读器页就行？

```
Edge 浏览器打开"阅读器页"
  = 浏览器真的把页面加载了，页面里的签名程序(WASM)运行起来了
  = 这时候在页面里发请求，浏览器自动算好签名
  = 微信读书一看"哦，是正常浏览器在正常页面里请求" → 放行 ✅
```

**打个比方：**
```
微信读书 = 一栋有门禁的大楼
Python 直接请求 = 打电话报门禁号 → 门卫要求刷脸 → 你没法刷 → 拒绝
Edge 开着阅读器页 = 一个真人站在摄像头前 → 刷脸通过 → 放行
宿主机代理 = 一个"办事员"，替你把请求递给那个真人
```

### 为什么要"你的"Edge？

- 需要**微信读书登录态**（Edge 里登录着微信读书，有你的 cookie）
- **真实浏览器**不容易被微信读书识别成自动化工具
- 所以必须借用你真实登录的 Edge

### 为什么"阅读器页"？

微信读书规定：请求必须在**阅读器页上下文**里发出才有效（它靠这个判断"是不是真人在正常使用"）。打开任意一个公众号的阅读器页就够了——**一个阅读器页可以查询所有公众号**。

## 六、宿主机代理是干嘛的？（翻译官）

```
容器(WeRSS)  ──POST http://host.docker.internal:9000/fetch──→ 宿主机代理（9000）
     "我要 MP_WXS_3089223813 这个号的文章"                    │
                                                             ▼
宿主机代理 ──CDP指令──→ Chrome浏览器（在阅读器页执行fetch）
     "在页面里帮我发这个请求"                                   │
                                                             ▼
宿主机代理 ←──文章JSON─── Chrome浏览器
     │
     ▼
容器(WeRSS) ←──文章JSON───  (采集器拿到数据，存进数据库)
```

**为什么要中间加个代理？** 因为 WeRSS 跑在 Docker 容器里，容器里没有你那个登录好的 Edge。代理就是**宿主机上的一个中转站**，让容器能指挥你的 Chrome。
- **流程**：网站后端 --9000--> 代理 --9222/9223--> 一个个 Chrome
- 9000 是host_weread_agent的端口，当网站后端要抓数据时，通过9000这个端口找代理程序
- 9222、9223 是每个 Chrome 自己的遥控门牌号。你在服务器上以调试模式启动 Chrome 时，给了它一个参数 --remote-debugging-port=9222，等于给这个 Chrome 装了个"遥控器接口"，别的程序就能通过这个接口指挥它（开页面、执行代码）。
- 把端口想成门牌号/电话分机。代理程序启动后确实在干活了，但它只在自己机器上"开了一扇门"，等着别人敲门。we-rss-mp 容器是另一个独立的程序，它和代理不共享内存，唯一的联系方式就是通过网络——它必须知道"去哪台机器、敲哪扇门"，也就是 IP + 端口。
- 这里的端口都是服务器上的端口，就相当于是门。we-rss-mp 容器也在这台服务器上，但它在"Docker 沙盒"里，从沙盒看服务器的门，地址就叫 host.docker.internal:9000（配置里那个 weread.host_agent 就是写这个）。代理就是通过 localhost:9222 去指挥那个 Chrome 的（localhost = 自己和代理在同一台机器）。

### 补充：CDP 是什么？

**CDP = Chrome DevTools Protocol（Chrome 开发者工具协议）**。

通俗理解：
- 就是你按 **F12 打开开发者工具**时，背后用的那套"遥控协议"
- 它允许程序通过 WebSocket 和浏览器对话：打开页面、执行 JS、读取数据
- 我们的**宿主机代理就是用 CDP 给 Edge 下指令**："在这个阅读器页执行 fetch"

```
F12 开发者工具 = 一个遥控器（你手动按）
CDP = 遥控器的"遥控协议"（背后那套指令标准）
宿主机代理 = 一个会编程的人，用协议自动指挥浏览器（不需要你按F12）
```

**一句话：CDP 是"程序控制浏览器"的通道，宿主机代理就是通过这个通道指挥 Edge 的。**

## 七、自动化是怎么实现的？（定时任务）

系统不靠你手动点"更新"，靠**定时任务**：

```
你配置的"消息任务"：
  - 抓哪些号：空 = 抓所有公众号
  - 什么时候抓：cron = "0 9,21 * * *" = 每天 9:00 和 21:00
        ↓ 到点自动触发
  - 后端启动采集器 → 对所有公众号逐个抓取 → 存数据库
```

**你添加新公众号也会自动纳入**：
```
你添加新号 → 下次定时任务(9点/21点)自动把它也抓了
```

## 九、关于 Cookie 的真相（用没用上？）

**核心答案：采集文章列表用的不是 `.env` 里那个 Cookie，而是 Edge 浏览器自己的登录态。**

```
微信读书登录态 = Edge 浏览器里的登录
    ↓
Edge 在阅读器页发请求时，自动带上【Edge自己】的cookie
    ↓
所以真正起作用的是"你在Edge里扫码登录微信读书"这件事
    ↓
.env 里的 WEREAD_COOKIE 反而不是采集的核心（它是早期方案留下的）
```

**那 `.env` 里的 Cookie 和"微信读书管理页"还有用吗？**
- `.env` 的 Cookie：用于"微信读书管理页"的状态显示，以及（如果启用全文抓取）部分请求。**采集文章列表本身不用它。**
- **微信读书管理页**：可选的锦上添花。你现在的 Cookie 已配在 `.env`，管理页不做也不影响采集。
- **真正要维护的登录态**：是 **Edge 里的微信读书登录**。Edge 里掉线了 → 重新扫码即可。

**所以你的直觉基本对**：采集核心不靠 `.env` Cookie，靠的是 Edge 的登录。

## 十一、常见疑问快答

**Q: 为什么不直接用公众号后台接口抓？（以前的方式）**
A: 腾讯 2026年7月底关闭了公众号后台的跨账号查询接口，那条路废了。微信读书是现在还通的路。

**Q: 为什么一定要开着 Edge？**
A: 微信读书的签名只能由真实浏览器算出来。关了 Edge，没人算签名，抓不了。

**Q: 微信读书里没关注的公众号能抓吗？**
A: 能。抓取不要求先关注，只要这个号在微信读书的收录目录里即可（大号基本都在）。关注只是为了书架里方便查看。


**Q: 我电脑关机了，还能抓吗？**
A: 不能。采集依赖你电脑上的 Edge 和代理。要一直抓，电脑就得开着（或设开机自启）。

**Q: `.bat` 和 `.py` 是什么区别？**
A: 以 `手动更新所有公众号` 为例，是两个文件配合：
- `手动更新所有公众号.bat` = **按钮**（Windows 启动器，双击运行）
- `manual_update.py` = **发动机**（Python 脚本，真正干活）
- 你只需要**双击 .bat**，它会自动调用 .py。.py 不用你碰。
- 同理 `start_weread_host.bat` 也是按钮，双击它启动 Edge + 代理。

**Q: 开机自启动是啥？**
A: 让 Edge + 代理在**电脑开机时自动启动**，不用你每次手动双击。这样定时任务(9点/21点)执行时，Edge 和代理一定在运行，不会因为"忘了启动"而抓取失败。

## 十二、部署到服务器时的考虑（重要）

**网站本身**（前端 + 后端 + 数据库 = 4个容器）部署到服务器没问题，**但采集部分有硬性限制**：

### ⚠️ 核心限制
采集必须依赖一个**真实登录了微信读书的 Edge 浏览器**（算签名）。服务器通常是**纯命令行、没有图形界面**，没法像本地那样"打开 Edge 扫码登录"。

### 三种部署方案对比

| 方案 | 能跑网页 | 能采集 | 复杂度 |
|---|---|---|---|
| A. 服务器只跑4容器 | ✅ | ❌ 不能（无Edge扫码）| 低 |
| B. 服务器硬上 Edge | ✅ | ⚠️ 能但要折腾 | 高 |
| C. 本地采集 + 服务器网页 | ✅ | ✅ | 中（要同步数据库）|

**方案 B 的做法**（如果你必须全放服务器）：
```
服务器装 Linux 图形环境(Xvfb虚拟显示器) + Edge
→ 通过 VNC 或网页看登录二维码 → 扫码登录一次
→ Edge 常驻后台，session 保存在配置里
```
可行，但配置繁琐，且 Edge 在服务器上更容易被微信读书识别。

**推荐**：如果你要正式部署，优先考虑 **方案 A/C**——服务器负责展示文章，采集要么本地跑，要么等上游作者将来解决签名问题（他们很活跃，可能有纯服务端方案）。

### 手动更新脚本（部署前先会用手动）
- `tools\start_weread_host.bat` → 启动 Edge + 代理
- `tools\手动更新所有公众号.bat` → 一键触发全量抓取

## 十三、部署到服务器的具体步骤（实操）

> **部署 = 原来的项目(4个容器) + 一个"宿主机代理"(小程序) + 一个浏览器(Chrome)。**
> 不是另起一个程序，是在原项目上加了一个辅助组件(因为微信读书升级反爬后, 原采集方式失效, 需要浏览器+代理当"桥梁")。

### 第一次部署（含采集环境，只做一次）

**① 网站部分（4个容器）：**
```
本地打包:  tar -czf ai-report.tar.gz (排除.git/node_modules)
上传:      scp ai-report.tar.gz we_mp_rss.sql 用户@服务器:~
服务器:    tar -xzf → docker compose -f compose/docker-compose.local.yaml up -d --build
数据库:    本地 mysqldump → 上传 → 服务器 restore
```

**② 采集环境（只装一次）：**
```
上传: server-weread.tar.gz (含 agent/脚本)
运行: bash tools/server_install.sh      # 装 Xvfb + Chrome + Python依赖
运行: bash tools/server_start_weread.sh # 启动 Xvfb + Chrome + 代理
扫码:  打开 http://服务器IP:9000/qr → 用微信扫码登录微信读书(只此一次)
```

### 后续每次更新代码
```
只需要重做"①网站部分"(重新打包上传+compose up -d --build)
采集环境不用重装, 登录态不用重新扫码
```

### 服务器重启/开机后
```
运行: bash tools/server_start_weread.sh   # 重新启动 Xvfb + Chrome + 代理
（登录态保存在 Chrome 配置里, 不用重新扫码）
```

### 微信读书登录失效时
```
打开 http://服务器IP:9000/qr 看是否要重新登录
若要登录: http://服务器IP:9000/click?text=登录 → 刷新 /qr → 扫码
```

### 关键文件清单
| 文件 | 作用 |
|---|---|
| `tools/host_weread_agent.py` | 宿主机代理(容器和浏览器之间的桥梁, 含/qr截图和/click点击) 后台小程序，网站后端要拉文章列表时，负责去操作chrome抓数据|
| `tools/server_install.sh` | 服务器装环境(一次性) |
| `tools/server_start_weread.sh` | 启动采集服务(Xvfb+Chrome+代理) |

# 账号池缺陷
- 状态纯内存、无持久化：ACCOUNT_STATUS 是内存 dict，agent 一重启全部变 unknown，登录态、错误历史全丢。
- 无单实例锁/守护：能开两份抢 9000 端口，挂掉没人拉起，接口超时静默。
- failover 会"雪崩式"打爆下一个号：换号是按 CHROME_PORTS 顺序轮（host_weread_agent.py:162），所有哈希到坏号的请求都涌向同一个下一账号，容易连环限流；且状态记录的是"最后尝试的号"，页面看不出到底哪个号坏了。
- 无每账号限速/串行化：每次请求新开 websocket，jobs/mps.py:70 只对公众号间随机 sleep，但任务队列多线程并发，同一 Chrome 可能被同时打 → -2014。
- 登录链路脆弱：扫码后没有轮询确认登录成功，状态不会自动变 ok；二维码靠点"登录"按钮 + 硬编码 sleep（5-8s），微信改版就失效。
- 认证双源割裂：列表用 Chrome 里的登录态，正文用 config 里的 WEREAD_COOKIE（.env:13），两边会话过期时间不一致，一个能用一个 401。
- 账号管理仅 Linux 可用：spawn_chrome/remove_chrome 用 pkill、DISPLAY=:99、which google-chrome（host_weread_agent.py:327,374），你在 Windows 上"添加/移除账号"会失败。
- 同 IP 单点：所有 Chrome 走同一出口 IP，IP 被封则全挂，账号池只解决账号级不解决 IP 级问题。
- 无健康探测/告警：会话过期只能等下次抓取撞到 -2010 才知道，没有主动检测和通知（老的公众号渠道还有 send_wx_code 通知，账号池没有）。
账号池的缺陷，逐个翻译成人话
1. 状态只记在"脑子里"，不写到"纸上"
程序运行时的状态（哪个号登录了、哪个号报错了）只存在内存里。程序一重启，全部清零，页面就变成"unknown"。就像记账只靠脑子记，一关机全忘。
2. 没人看着它，挂了没人管
没有"只能开一份"的限制（所以才会启动两份），也没有守护机制：程序崩了不会自动重启，一直挂到你去手动看。
3. 一个号坏了，会把其他号也"传染"坏（雪崩）
设计的思路是：账号A报错 → 自动换账号B去试。但现在的换法很笨——所有该用A的请求都一股脑塞给B。B本来好好的，被这么多请求一压，也被微信读书限流拉黑了。等于救火没救成，还把隔壁烧了。
4. 请求不排队，容易触发限流
每次拉数据都像"打电话"，而且好几个任务可能同时给同一个 Chrome 打电话。微信读书一看"这账号怎么同时这么多请求"，就判定是机器人 → 限流（-2014）。理想做法是每个账号一个排队口，一次只放一个请求进。
5. 扫码登录没有"确认成功"这一环
登录流程是：导航到微信读书 → 点"登录"按钮 → 等几秒 → 截图。它只负责把二维码给你，你扫码之后它不会去检查"到底登没登上"，也不会主动把状态更新成"正常"。而且"点登录按钮"是靠找按钮上的文字，微信网页一改版就找不到。
6. 两套"身份证"，一套过期了另一套还在用
拉文章列表用的是 Chrome 里扫码登录的会话；拉文章正文用的却是配置文件里手动填的 Cookie（.env 里那个 WEREAD_COOKIE）。这俩是两回事，过期时间不一样。结果可能：列表能拉到，正文全 401（说"你没权限"）。应该统一只用一套。
7. 都在一根"网线"上，IP 被封全挂
所有 Chrome 都是通过同一台服务器的同一个公网 IP 出去上网的。微信读书如果封了 IP（而不是封账号），那不管你有几个账号，全部一起死。账号池只解决"换账号"，解决不了"换 IP"。
8. 号过期了没人通知你
账号会话过期，只能等到某次抓取撞上 -2010 才知道。没有"定期体检"去主动查号还活着不，也不会像老渠道那样发个微信/飞书提醒"请去重新扫码"。所以经常是你发现的时候已经趴了一两天了。

# 命令行
## 杀死进程
- pkill -f host_weread_agent.py：按名字杀掉所有正在运行的 host_weread_agent.py 进程（pkill=按进程名杀，-f=按完整命令行匹配）。相当于"先让旧的代理下班"。
- sleep 1：停 1 秒，等进程彻底退出、别和新起的打架。
- nohup python3 host_weread_agent.py > ~/weread-agent.log 2>&1 &：启动新的代理。拆开看：
- nohup：让程序在后台跑，并且你关掉 SSH 窗口它也不死；
- > ~/weread-agent.log：把程序打印的信息存到日志文件里；
- 2>&1：错误信息也一起存进同一个日志；
- &：放到后台执行（命令立刻结束，程序继续跑）。

ps = process status（进程状态），就是"把正在运行的程序列出来"。a=所有用户的，u=带详细信息，x=包括后台程序（连没绑定终端的也算）。所以 ps aux | grep host_weread_agent 整句意思是：列出所有程序，再过滤出名字里带 host_weread_agent 的行，用来数它开了几份。你的理解完全正确，它就是"任务管理器"的命令行版。
