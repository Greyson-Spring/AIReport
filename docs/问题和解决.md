## 1 删除账号不清用户数据、新账号不自动开阅读器页
多日没有登录账号，显示2010错误，没有重新登录的选项，只能先移除账号，重新登录。当重新登录后，发现原始账号在上面，因为代码设计并没有删除用户数据文件夹，导致从新打开一个chrome网页任保留之前登录信息，之前登录应该是有效的，估计是微信读书零食返回的错误

## 2 前端卡死，点击账号池后点击别的菜单栏，卡顿
根因是 apis/account_pool.py 里这些（账号池页面每个账号卡片会自动加载一张二维码截图）接口写成了 async def，里面却是会阻塞几十秒的网络调用（尤其 /qr 会等 Playwright 截图）。FastAPI 的 async def 跑在主线程上，一个 /qr 卡住，整个后端所有接口都得排队等它——你在账号池页面上每个账号卡片会自动加载一张二维码截图（img），点击订阅管理时它要请求数据，正好撞上这个阻塞，就卡几秒。改成普通 def，让 FastAPI 丢到线程池里跑，就不阻塞别人了。

关于 async 卡死的解释
你说的没错，"异步（async）本身是好的"。问题出在用错了地方，这是个很经典的坑：
FastAPI 的规则：async def 接口是跑在"唯一的主线程"上的，所以它里面的每一个操作都必须是秒办完的（非阻塞）。如果你的 async def 里放了一个会干等 60 秒的同步网络请求（原来的 /qr 就是这么写的），主线程就被它死死占住，网站上所有其他接口（不管是不是 async）全都得排队等它——你点"订阅管理"要请求数据，正好排在它后面，就卡了几秒。
打个比方：async 接口就像"一个前台，边接电话边回微信"——但这有个前提，每件事都得是秒办的。如果你塞给前台一个"必须干等 60 秒"的任务，她就被钉在原地，所有电话都接不了。
修复方式：把这几个接口从 async def 改成普通 def。FastAPI 遇到普通 def 接口，会自动把它丢到线程池里跑——相当于多请了几个前台，每个慢请求只占用一个前台，不影响其他人。
一句话总结：bug 不是"用了异步"，而是"把会阻塞的同步操作错塞进了 async 接口"。这也是为什么之前"都说不阻塞好"，现在却要改成 def——在这个位置，普通 def 才是对的做法。

## 3 利用utf8的csv格式导入多个公众号，导入成功但不显示，且没抓取文章

- 没显示在"未分类公众号"
"未分类公众号"列表来自接口 /wx/mps，它只返回当前用户"已订阅"的号（apis/mps.py:266 通过 user_feeds 订阅表关联查询）。但旧的导入代码只把数据塞进了 feeds 表，从没创建你的订阅记录（user_feeds）——号在数据库里，但你没"订阅"它，所以列表里看不到。
- 没更新文章
旧导入代码只插入行，不会触发抓取任务（而正常的"添加公众号"流程 apis/mps.py:594 会排队抓取）。所以导入的号 update_time 一直是 0，一篇文章都没抓。update_time存的是上次抓到最新一篇文章的发布时间，这个字段的作用是决定下次抓取时抓多深。
### 解法
1. 创建/恢复你的订阅关系：导入的每个号（新增或更新）都自动创建 user_feeds → 会出现在"未分类公众号"。
2. 自动触发抓取：新增的号、以及 update_time=0（从没抓过）的号，导入后自动排队抓文章——和单条"添加公众号"行为一致。
3. 附带加固：id 为空时从 faker_id 反推；空值不覆盖已有数据；缺 id 和 faker_id 的行跳过不报错；提示信息直接显示"新增/更新/跳过/已触发抓取"几个数。

## 4 自定义文件夹显示文章速度慢
点文件夹时，fetchArticlesByFolder（ArticleListDesktop.vue:954）会对文件夹里每个公众号单独发一次 HTTP 请求（每个要 20 条），文件夹有几个号就发几次，再把结果在前端拼起来排序。而点"全部"只发一次请求、数据库直接分页返回（fetchArticles，apis/article.py 一次查询带 LIMIT）。
所以文件夹越复杂越慢，跟数据量无关——是"N 次请求"vs"1 次请求"的区别。我来改成后端一次性按文件夹查（和"全部"一样快）。

### 解决

我改了两处：后端接口 + 前端。
后端（apis/article.py）：文章接口新增了一个 folder_id 参数。收到它时：
1. 先查 folder_feeds 表（文件夹↔公众号关联表），拿到这个文件夹里所有公众号的 id 列表；
2. 然后一条 SQL：WHERE mp_id IN (文件夹里的那些公众号id)，按发布时间倒序、数据库分页（OFFSET/LIMIT）返回。
也就是说，"合并文件夹里所有号的文章"这个动作由数据库一条 SQL 完成——把所有文章混在一起按时间排序，只取当前页那几条。和你点"全部"用的是同一套逻辑，只是把"全部订阅的号"换成"文件夹里的号"。
前端：点文件夹时不再一个号发一次请求，只发一次 GET /wx/articles?folder_id=xxx，翻页也是后端分页。
一句话：以前是"前端把每个号的文章分别拿回来手动拼"，现在是"后端一条 SQL 一次查完"。所以文件夹里号再多，也和"全部"一样快。

### 真正触发抓取的时机有4个
- 定时任务（jobs/mps.py 的 cron）
- 文章列表页点"更新"按钮（/wx/mps/update/{id}，注意有 60 秒防频繁更新限制）
- 添加公众号时（apis/mps.py:594 会自动排队抓一次）
- 导入时（旧代码没有这个，我刚补上了）

# 数据流

前端发请求→ 服务器上的程序（后端）→查数据库sql→ 返回前端→渲染页面
这部分不需要在经过后端了是吗





一、先讲"前后端到底是怎么衔接的"（核心框架）
你的理解没错，流程就是：
浏览器里的页面(前端)  --发请求-->  服务器上的程序(后端)  --查数据库-->  MySQL
前端拿到返回的数据  -->  渲染成你看到的列表/页面
拆开是 7 步：
1. 前端代码里有个函数叫 getSubscriptions({page, pageSize})（在 web_ui/src/api/subscription.ts 里定义）；
2. 这个函数内部用 http（一个叫 axios 的工具）发出一条 HTTP 请求，实际发出的地址是：
http://服务器IP:8001/api/v1/wx/mps?offset=0&limit=100
3. 这条请求通过网络飞到服务器的 Python 程序（FastAPI，监听 8001 端口）；
4. FastAPI 拿 URL 里的路径 /api/v1/wx/mps 去匹配后端定义的接口（apis/mps.py 里 @router.get("")，路由前缀 /mps，挂在 /api/v1/wx 下）——*两边路径能对上，这就是衔接的"规则"*；
5. 后端函数开始干活：查数据库（SQLAlchemy 查 MySQL）→ 拼成 JSON → 返回：
{"code":0, "data":{"list":[...], "total":128}}
6. JSON 通过网络飞回浏览器；
7. 前端的 http 工具把 JSON 解包，getSubscriptions 拿到 list，组件把它塞给 unassignedMpList 这个变量 → Vue 检测到变量变了 → 自动重新渲染侧边栏。
一句话规则：前端发"请求(URL+参数)"，后端回"数据(JSON)"，两边靠"路径和参数约定一致"衔接。 这就是所有前后端分离开发的通用模式，不是这个项目特有的。
二、我是怎么快速定位到那一行的
不是猜的，是*"从你看到的东西，倒着往回查代码"，中间全靠搜索关键词*。
你看到的症状是"侧边栏未分类只显示 101 个"。"侧边栏"是页面上看得见的东西，那就一定有一个变量在控制它。我的思路：
第 1 步：找到控制侧边栏的变量
用搜索工具（grep）在 ArticleListDesktop.vue 里搜"未分类"相关的英文关键词，找到 unassignedMpList（未分类公众号列表变量）。
第 2 步：找到"谁给这个变量喂数据"
搜 unassignedMpList，看到它在一个叫 buildLeftSidebarData（构建左侧数据）的函数里被赋值，赋值来源是 allFeeds。
第 3 步：找到"allFeeds 从哪来"
再往上看这个函数开头，就看到了 getSubscriptions({ page: 0, pageSize: 100 }) ——**"只取前 100 个"**。这不就对上了吗？你订阅了 128 个，但前端只申请 100 个，所以显示 101（100 个 + 1 个"精选文章"）。
第 4 步：验证后端是不是也有限制
搜后端 apis/mps.py 里的 limit，看到 le=100（上限 100）——前端要 100，后端最多给 100，双重限制，坐实了。
核心方法总结成一句话：
从"页面上的现象"出发 → 找控制它的变量 → 找给变量赋值的函数 → 找函数调用的接口 → 找后端路由 → 找数据库查询。每一步都用搜索（grep）跳转。
程序员的日常有很大一部分就是"在代码里搜关键词"，搜到线索顺着往下追，跟查案一样。
三、开发都是这样吗？
是的。这个项目是标准的前后端分离：
- web_ui/src/views/ 存"页面"（.vue）
- web_ui/src/api/ 存"每个页面调后端接口的说明书"（.ts，一个接口一个函数）
- apis/ 存"后端接口"
- core/models/ 存"数据库表的样子"
衔接规则就一条：前端 api/*.ts 里写的路径（如 /wx/mps）必须和后端 apis/*.py 里注册的路由一致，两边参数名一致，数据格式约定为 JSON。这就是"契约"。Vue、React、FastAPI、Spring 全都是这个套路，学会一个就懂全部。
四、给你一套可复用的排查框架
以后遇到"页面显示不对"，按这个顺序查，一定分清楚是前端的锅还是后端的锅：
第 0 步：先问"数据对不对？"
打开浏览器按 F12 → Network（网络）标签 → 刷新页面 → 找到对应的请求（比如名字带 mps 或 articles）→ 点开看 Response（响应）里的 JSON 数据：
- 如果 数据是对的（128 条都在）但页面只显示 101 → 前端渲染问题 → 去查前端。
- 如果 数据本身就少（只有 100 条）→ 后端问题 → 去查后端接口和 SQL。
- 如果 请求根本没发出去 → 前端问题。
这一步就能砍掉一半的排查范围，是最高效的一招。
第 1 步：后端接口可以直接"人工试"
后端接口可以脱离页面单独验证——在服务器上直接敲：
curl "http://localhost:8001/api/v1/wx/mps?offset=0&limit=200"
看它返回的 JSON 里到底有多少条。等于"跳过前端，直接问后端要数据"。后端有没有毛病，一敲就知道。
第 2 步：数据库可以直接查
还不放心就再往下挖一层，直接 SQL 查库（就像这次用 SELECT COUNT(*) ...），确认数据本身对不对。这样就分清了：数据层（数据库）→ 接口层（后端）→ 渲染层（前端），一层一层往下排除。
第 3 步：定位到具体函数后，用搜索顺着"调用链"追
- 前端：变量 → 赋值函数 → api函数 → URL
- 后端：URL → 路由函数 → SQL

## 6 采集只抓列表不抓正文（正文缺失、AI摘要没料）
### 问题现象
- 文章"更新成功"但正文是空的；点开文章正文空白；AI摘要只能用标题+摘要。
### 根因
- 采集分两步：① 抓列表（url/标题/时间/摘要）② 抓正文。默认配置 GATHER_CONTENT=False，只做①不做②。
- "更新成功" = 只抓到"索引"（标题/链接/摘要），不代表正文爬到了。
### 解决
1. config.example.yaml 默认改 True；服务器 .env 必须写 `GATHER.CONTENT=True`（**带点号**，见问题9）。
2. weread_mp.py：部分正文抓取失败不再中断整个公众号更新（原来会 raise 导致整个号更新失败）。
3. 补抓脚本 tools/backfill_content.py：对指定公众号所有空正文文章一键补抓（docker exec 里用虚拟环境 python 运行）。

## 7 正文抓取的三条通道（为什么"有的有正文有的没有"）
| 通道 | 原理 | 状态 |
|---|---|---|
| ① 账号池 weread 通道 | 在已登录 Chrome 里 fetch `/web/mp/content?reviewId=` | 最稳，但需要 Chrome 开着微信读书阅读器页，否则 NO_READER_PAGE |
| ② web 通道 | Playwright 无头浏览器爬 `mp.weixin.qq.com/s/xxx` | 容器里没装浏览器 → 一直失败 |
| ③ api 通道 | requests 直接 GET 文章 URL | 能用，但会被反爬随机拦"环境异常" |

- 之前正文缺失，主因是②（Playwright 没装）和 weread cookie 过期，不是"爬 URL 这条路一定被拦"。
- 现在顺序：账号池 → web → api，哪个成功用哪个。

## 8 文章图片不显示（防盗链 + 误删 + 懒加载）——多层根因
### 问题现象
- 有的文章图片显示"此图片来自微信公众平台、未经允许不可引用"；有的文章完全没有图片；F12 有 405 报错（微信脚本在站内执行）。
### 排查出的多层根因
1. **防盗链**：`mmbiz.qpic.cn` 图片在非微信域名加载带 Referer → 微信拒绝 → 占位图。
2. **误删所有图片**：tools/fix.py 里 `remove_attributes=[{'src': ''}]`，而 clean_html 的实现是"value 为空时匹配所有带 src 的元素并删除" → 每次显示正文把所有 `<img>` 删光 → 完全没图。
3. **微信懒加载**：图片真实地址在 `data-src` 不在 `src`；若没转成 src 且微信 JS 被禁 → 没图。
4. **详情页原样渲染**：`views/article_detail.py` 直接输出原始 `article.content` → 微信脚本原样执行（405）、图片未归一化/未代理。
### 解决
- 前端 ProxyImage（constants.ts）：把 mmbiz.qpic.cn/qlogo.cn/mmecoa.qpic.cn 图片 src 改走 `/static/res/logo/` 代理。
- 后端 apis/res.py：代理转发图片（去 referer）+ 缓存 + 保留原 URL 查询参数（wx_fmt 等）。
- tools/fix.py 重写：`normalize_article_images`（data-src→真实src、删空/占位图）+ 去掉误删写法 + 清 script/link/head + 图片代理前后各重写一次。
- views/article_detail.py：详情页正文也走 fix_html。
- 验证：F12 看 img src 应为 `/static/res/logo/https://mmbiz.qpic.cn/...`；405 报错应消失。

## 9 环境变量名带点号的坑
- config 读 `${GATHER.CONTENT:-...}` 是**原样取环境变量名**（os.getenv），所以 .env 里必须写 **`GATHER.CONTENT=True`（带点号）**。
- 写 `GATHER_CONTENT=True`（不带点号）**不生效**，会静默回退到默认值 False。
- 同理 `GATHER.CONTENT_AUTO_INTERVAL=10`（带点号）才是补抓间隔。
- 排查这类问题：`docker exec we-mp-rss-local env | grep GATHER` 看容器里实际生效的值。

## 10 服务器/容器环境注意点（今天踩过的坑）
- 代理（host_weread_agent.py）跑在宿主机，**改了代码要 pkill 后重启**才生效；"文件是最新 ≠ 进程是最新"。
- 容器里默认 `python` 不存在，要用 `python3`；且依赖装在虚拟环境里，要 `/app/env_x86_64/bin/python`（或 `ls -d /app/env*/bin/python` 找）。
- 容器里 Playwright 浏览器没装 → web 通道不可用（需要时可 `INSTALL=True` 重建）。
- 服务器 `.env` 在 `~/AIReport` 目录（不在 tools 下）。
- 重建容器用 `docker compose ... build --no-cache we-mp-rss` 可避免 Docker 旧缓存层导致"改了没生效"。

## 11 文章列表打开极慢(40秒), 全站跟着卡
### 现象
- 一打开网站右侧文章一直转圈; "全部"、文件夹、单个公众号都要 40s+ 才显示。
### 排查过程(逐层排除)
1. 计时接口: 单个公众号 1.4ms,"全部" 41s → 是后端查询慢, 不是前端/网络。
2. docker stats: CPU 仅 2.5% → 不是后台任务抢资源。
3. 重启容器清掉 Sleep 连接 → 仍 34s → 不是连接池问题。
4. EXPLAIN 主查询: `type=ALL`(全表扫描)+`Using filesort`, `possible_keys=NULL` 一条索引都没用。
5. 分段测: 隐藏表只有 2 行、索引都在; 订阅 IN 正常 → 问题在 SELECT 里的 `has_content` 判断。
### 根因(两层)
1. **列表查询读了正文大字段**: SELECT 里 `CASE WHEN content<>''` 用来算"有没有正文"。MySQL 为排序/扫描, 要把 2.3 万篇的 `content`(TEXT 大字段)全读一遍 → 40s。
2. **async def 阻塞**: 该查询写在 `async def` 里(内部是同步阻塞 SQL), 一次慢查询会卡住整个 FastAPI 事件循环 → 期间点文章/切页全部排队。
### 修复
1. apis/article.py: 列表查询只查 `ArticleBase` 轻量列, 不再读 `content`; `has_content` 改为只对返回的 10 篇单独判断(只读 10 篇正文, 快)。
2. 订阅过滤: 128 个 `OR` 合并成单个 `mp_id IN(...)`(走索引)。
3. `get_articles` 由 `async def` 改普通 `def`(线程池执行), 慢查询不再阻塞全站。
### 验证
- "全部"从 41s → 1s 以内。

## 12 后端接口与数据库操作、认证鉴权原理(小白版)
### 12.1 类和对象不是一回事
- **类(class)=图纸/模板**: 定义有什么属性、结构, 本身没有真实数据。
- **对象/实例(object/instance)=按图纸造出来的具体实物**: 每个实例带着真实数据。一个类可造很多实例。
- `session.query(ArticleBase)`: 不是"创建一个对象", 而是把**类(表模型/图纸)**交给 SQLAlchemy 说"查这个类对应的表", 返回**查询构建器**; 继续 `.filter()/.order_by()/.limit()`, 最后 `.all()` 才执行, 拿到的**每个元素才是 ArticleBase 实例**(一行数据)。
- 类不是空的: 它装着**表结构描述**(那些 `Column` 定义:id 列、title 列……), 这是"说明书", 不是某行数据。
### 12.2 ORM / SQLAlchemy 是啥
- **SQLAlchemy = 把 Python 表达式翻译成 SQL 的工具(ORM)**。
- `.filter() .order_by() .limit() .count() .all()` = 查询构建器上的**查询 API 语法**。
- `.filter(Article.mp_id == 'x')` 里的 `==` **不是数值比较**, 是 SQLAlchemy **重载运算符**用来"搭 SQL 条件"(生成 `WHERE mp_id='x'`)。`!=`、`.in_([...])`、`and_()`、`or_()` 同理。
- 例: `session.query(Article).filter(Article.mp_id=='x').order_by(...).limit(10)` → `SELECT * FROM articles WHERE mp_id='x' ORDER BY ... LIMIT 10`。
### 12.3 模型文件与表
- `core/models/article.py`: `class ArticleBase(Base)` 对应表 `articles`(轻量列, 不含正文) + `class Article(ArticleBase)` 加 `content/content_html`(含正文大字段)。
- 程序启动时 `Base.metadata.create_all()` **自动建表**(表不存在时)。
- **一个类=一张表, 一个属性=一列, 一行结果=一个实例**。
### 12.4 DB 和 session
- `DB` = `core/db.py` 里的 `Db` 实例(数据库"总管", 持有引擎+连接池)。
- `DB.get_session()` = 从连接池拿一个会话(办事窗口)。
- 用 `session.query(...)` 操作, 结束 `session.close()` 关窗口。
### 12.5 后端接口怎么定义(get_articles 拆解)
- `@router.api_route("", methods=["GET","POST"])`: 装饰器把函数注册成接口, `""` 是路径(最终 = `/api/v1/wx/articles`), methods 表示支持的请求方式。
- `offset: int = Query(0, ge=0)`: 声明一个 URL 查询参数 `?offset=10`, 默认 0, 校验 >=0; FastAPI 自动从网址取值并传进函数。
- `current_user: dict = Depends(get_current_user_or_ak)`: **依赖注入**——FastAPI 先调用 `get_current_user_or_ak` 验证登录用户, 再把结果传进来(这就是认证入口)。
- 函数最后 `success_response({list, total})` → FastAPI 转成 JSON 返回前端。
### 12.6 认证鉴权怎么实现
- **登录**: 前端 POST `/api/v1/wx/auth/login` 用户名密码 → 后端查 users 表, 用 `pwd_context.verify(明文, 哈希)` 比对(库里存的是**密码哈希**, 不是明文) → 对上了就签发 **JWT token**(带签名 + 过期时间)。
- **之后每次请求**: 前端请求头自动带 `Authorization: Bearer <token>`。
- **后端**: `Depends(get_current_user_or_ak)` 读 token → `jwt.decode(token, SECRET_KEY)` **验签 + 验过期** → 通过就把用户身份返回给接口; 验不过/过期 → 401 → 前端跳登录页。
- **安全靠什么(四保障)**: ① 密码哈希存储; ② JWT 签名防伪(服务端秘钥签发, 改不了); ③ 过期时间(默认 30 分钟); ④ 传输保护(内网/HTTPS)。另外 `get_current_user_or_ak` 还支持 AK/SK 给脚本用。
### 12.7 前端每次查询怎么传用户信息
- **不在 article.ts 里手动传**。
- `web_ui/src/api/http.ts` 的**请求拦截器**自动加: `config.headers['Authorization'] = 'Bearer '+token` —— 凡是走 http 的请求, 发出前自动带上凭证。
- article.ts 只写 `http.get('/wx/articles', { params })`, 不碰用户信息; 凭证由拦截器统一加。
- 后端每个接口用 `Depends(...)` 统一验 → 这就是"集中鉴权": 登录一次, 之后每次请求 token 自动带、自动被验证。
