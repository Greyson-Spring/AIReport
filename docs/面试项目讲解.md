## 二、项目完整流程解析（讲清楚每个环节）

### 2.1 一句话讲清

**定时任务触发 → 后端把"要抓哪个公众号"告诉宿主机代理 → 代理指挥一台已登录微信读书的 Chrome 在阅读器页里发请求 → 拿到文章 JSON → 存进 MySQL → 大模型按提示词生成摘要/报告 → 网页展示。**

### 2.2 端到端链路（分步）

```
① 触发    定时任务(cron) 或 网页点"更新"
② 选采集器 core/wx/base.py 的 Model() 按配置 GATHER_MODEL=weread_mp 创建采集器 MpsWereadMP
③ 发请求    weread_mp.py 把 {book_id, offset} POST 给宿主机代理 http://host.docker.internal:9000/fetch
④ 指挥Chrome host_weread_agent.py 按 bookId 哈希选一个账号端口(9222/9223)
             通过 CDP(WebSocket) 连该 Chrome → 找到"阅读器页" → 执行 JS:
             fetch('/web/mp/articles?bookId=MP_WXS_xxx&offset=0', {credentials:'include'})
⑤ 拿结果    Chrome 拿到微信读书返回的文章JSON → 作为JS返回值经CDP通道传回代理 → 代理回传给后端
⑥ 解析入库  parse_mp_articles 解析 → 每篇通过回调 UpdateArticle → DB.add_article 写进 MySQL
⑦ 抓正文    若开启 GATHER_CONTENT: 对每篇走"账号池通道 → api通道 → cookie兜底"抓正文
⑧ LLM摘要   读 LLM 配置 → 逐篇/整月调大模型生成摘要/报告 → 存库或导出
⑨ 展示     网页读 MySQL 渲染；RSS 订阅；导出 md/docx/pdf/json
```

### 2.3 架构与组件

```
浏览器(前端 Vue3)
  │ :8001
  ▼
容器 we-mp-rss-local (FastAPI后端 + 定时任务)
  ├─ MySQL(容器)  存 feeds/articles/user_feeds/用户
  ├─ Redis(容器)  缓存/队列状态
  ├─ singbox(容器) 抓取网络代理
  └─ 抓取时 POST host.docker.internal:9000
宿主机代理 host_weread_agent.py (:9000, 跑在服务器, 不在容器)
  └─ CDP → Chrome账号池(9222/9223, 各自扫码登录微信读书, 开着阅读器页)
```

| 组件 | 在哪 | 端口 | 职责 |
|---|---|---|---|
| we-mp-rss(FastAPI) | 容器 | 8001 | 网站/接口/定时任务 |
| mysql | 容器 | 3306 | 存储 |
| redis | 容器 | 6379 | 缓存 |
| singbox | 容器 | 7890 | 代理 |
| host_weread_agent.py | 宿主机 | 9000 | 抓取总开关 |
| Chrome 账号池 | 宿主机(Xvfb) | 9222/9223… | 已登录微信读书的浏览器 |

### 2.4 核心难点①：为什么必须"代理 + 真实 Chrome"？（必讲）

- 微信读书的文章列表接口 `/web/mp/articles` 需要**浏览器环境的动态签名**（x-wr-pa 系列）；
- 后端用纯 HTTP(requests) 直连会被拒（返回 -2041 风控）——**签名不是固定字符串，是浏览器 JS 现场算出来的**；
- 所以借用**一台已扫码登录微信读书的 Chrome**，让它在**阅读器页上下文**里发请求，浏览器自动带合法签名和登录态。
- 一句话：**"不是我去爬，是让一个登录着的真人浏览器替我去要。"**

### 2.5 核心难点②：账号池（多账号）

- 一个账号有**频率限制/风控**（-2014 限流、-2041 风控）；
- 方案：**每个账号 = 一台独立 Chrome**（独立端口 + 独立用户数据目录），按公众号 bookId **哈希分摊**到不同账号；某个账号报错就**自动换下一个**（failover）。
- 类比：多个微信号轮流发，别让一个号被打爆。

### 2.6 核心难点③：fetch + CDP 通道（小白详细版）

- `fetch()` 不是 Linux 命令，是**网页 JavaScript 里发网络请求的函数**；
- 代理通过 CDP（Chrome 调试协议，一条 WebSocket 通道）向 Chrome 发 `Runtime.evaluate` 指令，让阅读器页执行那行 fetch；
- Chrome 执行完，**把结果文本作为 JS 返回值**，原路通过 CDP 通道传回代理进程 → 代理再作为 HTTP 响应返回容器后端；
- **全程是"字符串在内存里传递"，不会下载到磁盘**。这是面试官常问的"数据怎么回来的"。

### 2.7 核心难点④：正文三通道

| 通道 | 原理 | 状态 |
|---|---|---|
| ① 账号池 weread | 在已登录 Chrome 里 fetch `/web/mp/content` | 最稳，需 Chrome 开着阅读页 |
| ② web | Playwright 无头浏览器爬原文 URL | 会被反爬随机拦 |
| ③ api | requests 直连原文 URL | 可用，偶尔被拦 |

代码顺序：**① → ② → ③**，哪个成功用哪个。之前正文缺失就是 ② 容器里没装浏览器、① 阅读页没开导致。

### 2.8 数据与表

- `feeds`：公众号（全局共享，id=MP_WXS_xxx）
- `articles`：文章（含 content 正文大字段）
- `user_feeds`：用户↔公众号订阅关系（多个用户看同一批号）
- 另有用户/收藏/已读/文件夹/消息任务等表

### 2.9 LLM 摘要/报告

- LLM 配置存在数据库 `config_management`（llm_api_url/key/model），网页"大模型配置"页可改；
- 单篇摘要：提示词 + 标题/链接/日期/正文 → LLM → 写回 `article.description`（网页展示）；
- 月度报告：把全部单篇摘要汇总 → 报告提示词 → 生成报告 → 导出 md/docx。

### 2.10 定时任务与队列

- cron 调度器按表达式触发"更新全部公众号"；
- **任务队列**：公众号逐个入队执行（多线程，随机间隔防限流）；
- **内容补抓队列**：专门捞"正文为空"的文章后台补抓。

### 2.11 部署（面试要能画出来）

- Docker Compose：mysql / redis / singbox / we-mp-rss 四个容器；
- **宿主机代理 + Xvfb 虚拟显示 + Chrome 账号池**在容器之外常驻（抓取必需）；
- 数据库自动建表（SQLAlchemy create_all）；三层环境变量配置（compose environment / .env / config.yaml）。

## 三、面试官可能问的问题 + 参考解答

### 3.1 项目介绍类

**Q: 介绍一下你这个项目。**
A:（用 2.2 那条链路讲 1 分钟，别背功能，讲"为什么这么设计"。）

**Q: 你在里面负责/做了什么？**
A: 从 0 搭建到部署排障（真实经历），并举例 2-3 个自己解决的坑（见 3.7）。

**Q: 项目难点是什么？**
A: 抓取反爬（真实浏览器+CDP）、账号池限流分摊、正文稳定性（三通道）、数据量下的性能（列表 40s→1s）、LLM 成本与失败处理。

### 3.2 架构/技术类

**Q: 前后端怎么通信？**
A: axios → URL `/api/v1/wx/...` → FastAPI 路由 → 查库 → JSON → 前端渲染；两边靠"路径+参数+JSON"约定衔接。

**Q: 为什么用 Docker Compose？多个容器怎么协作？**
A: 同一 yaml 自动进同一内部网络，服务名当主机名；环境变量传 DB/REDIS 地址；depends_on 控制顺序。

**Q: 宿主机代理为什么不在容器里？**
A: 容器重启会丢进程，而抓取要求 Chrome 常驻登录；代理放宿主机由 systemd 托管，稳定。

### 3.3 数据库类

**Q: 有哪些表？怎么设计的？**
A: feeds/articles/user_feeds…（见 2.8），一个公众号可被多用户订阅（user_feeds 中间表）。

**Q: 文章怎么去重？**
A: articles.id 唯一（公众号-文章reviewId），写入前 check_exist。

**Q: 表很大怎么办/查询慢怎么办？**
A: 索引(mp_id/publish_time)、列表查询不读 content 大字段、分批处理。

### 3.4 抓取/反爬类

**Q: 为什么不用 requests 直接爬？**
A: 动态签名 + 反爬，纯 HTTP 被拒（-2041），必须真实浏览器。

**Q: CDP 是什么？**
A: Chrome 调试协议，允许外部程序通过 WebSocket 指挥浏览器执行 JS、导航等。我们用它让 Chrome 在阅读器页里执行 fetch。

**Q: 遇到限流/风控怎么办？**
A: -2014 限流→等冷却；-2041 风控→停止重试+人工验证；多账号分摊+自动换号。

### 3.5 并发/性能类

**Q: 页面打开很慢怎么排查？（重点案例，你要会讲）**
A: 现象=文章列表 40s。排查链路：① 接口计时（单号 1.4ms / "全部" 41s）→ 排除前端/网络；② docker stats CPU 低 → 排除后台负载；③ EXPLAIN 显示全表扫描；④ 定位到 SELECT 里 `CASE WHEN content<>''` 让 MySQL 读全部正文大字段。修复=列表查询不读 content、has_content 只对返回的 10 篇单独算；同时把接口从 async def 改 def（慢查询不再阻塞整个后端）。

**Q: async 和普通 def 的区别？**
A: async def 跑在主事件循环，里面必须是"非阻塞"操作；如果塞同步阻塞调用（如 SQLAlchemy），会卡住全站。普通 def 由 FastAPI 丢线程池，慢请求只占一个线程。

### 3.6 认证/安全类

**Q: 登录鉴权怎么做的？**
A: 密码哈希存库 → 登录签发 JWT（签名+过期）→ 前端每次带 Authorization: Bearer token → 后端 Depends 验签+验过期。安全=密码哈希、签名防伪、过期、传输保护；另支持 AK/SK 给脚本。

### 3.7 踩坑类（你的王牌，务必准备成"现象→根因→解决"）

1. **"显示成功却没抓到文章"**：代理返回的 `NO_READER_PAGE` 字符串错误被当成 code=0 → 静默 0 篇。改：有 errCode 即抛错。
2. **文章图片不显示**：微信防盗链 + `clean_html` 的 `{'src': ''}` 空值误删所有 `<img>` + 懒加载 data-src。改：data-src→src、去掉误删写法、图片走 `/static/res/logo/` 代理。
3. **文章列表 40s**：SELECT 读 content 大字段全表扫描。改：列表不读正文，has_content 对返回 10 篇单独算；async→def。
4. **CSV 导入"成功但不显示/不抓"**：只写 feeds、没建订阅、没触发抓取。改：导入自动建订阅+触发抓取。
5. **大模型配置页 CORS**：浏览器直连被跨域拦；服务端脚本不受影响。
6. **.env 开关不生效**：config.yaml 读 `${GATHER.CONTENT}`（带点），.env 写了不带点的 `GATHER_CONTENT`。改：写带点。
7. **账号"移除再添加还是已登录/不出二维码"**：旧 Chrome 进程没释放文件锁，profile 删不干净。改：pkill -9 + 等 3s + rmtree 重试。
8. **点菜单卡几秒**：async def 里塞阻塞调用卡住事件循环。改：普通 def。

## 五、小白必补的基础概念（面试官一句话就能引出，你要能接住）

| 概念 | 一句话人话解释 | 在这个项目里 |
|---|---|---|
| **CDP** | 一个"遥控 Chrome"的接口协议 | 代理靠它让 Chrome 执行 fetch |
| **ORM / SQLAlchemy** | 用 Python 对象操作数据库，不用写 SQL | `session.query(Article)` = 查 articles 表 |
| **类 vs 对象** | 图纸 vs 按图纸造的房子 | `ArticleBase`=表模型，`article`=一行数据 |
| **回调函数** | 把函数传给调用方，时机到了它回头调你 | `CallBack=UpdateArticle` 把文章存库 |
| **JWT** | 带签名的登录"门禁卡"，含过期时间 | 登录后每次请求 Bearer token |
| **环境变量三层** | compose environment / .env / config.yaml(`${}`) | 改开关就改 .env |
| **async/def** | async 在主线程、必须非阻塞；def 在线程池 | 慢查询必须用 def，否则卡全站 |
| **Docker 镜像/容器** | 模板 vs 跑起来的实例 | compose 起 4 个容器 |
| **Xvfb** | 服务器的"虚拟显示器"，让 Chrome 隐形运行 | 抓取 Chrome 靠它 |
| **哈希分摊/failover** | 按规则分给多个账号；坏了自动换 | 账号池防限流 |
